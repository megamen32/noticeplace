# Локальная проверка контракта и отката Notice Place

Проверка собирает два зафиксированных Git-исходника, устанавливает предыдущий релиз, обновляет его до кандидата и откатывает тем же `deploy/noticeplace`. Все три процесса запускаются последовательно из активного каталога установки, слушают только loopback и используют одну временную SQLite-базу. Рабочие каталоги и база удаляются по завершении. Артефакты и отчёт остаются в указанном каталоге.

## Запуск

Нужны Linux, Git, Bash, tar, zip, sha256sum, Node.js 18+ с npm и Python 3.10+ с локальными pip, setuptools ≥68 и wheel. Обе ревизии должны быть доступны локально. Выбирайте доверенные коммиты, так как проверка запускает их сборщики и код. Сборка SDK и их установка выполняются без обращения к индексам пакетов.

```bash
output=$(mktemp -d /tmp/noticeplace-release-contract.XXXXXX)
python3 -B scripts/check-release-contract.py \
  --previous 3969f5a24250c9924c60c7cf04c4155183dba82a \
  --candidate HEAD \
  --output "$output"
```

`HEAD` разрешается в конкретный SHA до сборки. Незакоммиченные изменения не попадают в артефакты. Для проверки версии 0.1.17 в качестве точки отката можно указать `800202ede0d344313a9efafac6aacea08da7c4d3`. Для каждого прогона нужен отдельный пустой каталог.

Связанные тесты репозитория запускаются отдельно. Тесты проверки публикации используют временный локальный Git-репозиторий.

```bash
python3 -m pytest -q \
  tests/test_release_contract_gate.py tests/test_deploy_lifecycle.py \
  tests/test_r40_deploy_publication.py tests/test_http_api.py \
  tests/test_ready_mcp_binding.py tests/test_mcp_actor_policy.py tests/test_notify_mcp.py \
  tests/test_notification_center_clients.py tests/test_sdk_health_contract.py
```

## Условия прохождения

| Контракт | Что проверяется |
| --- | --- |
| HTTP | `notify.event.v1` принимается с 202. Повтор с тем же ключом возвращает те же идентификаторы. Изменённый повтор даёт 409, чтение токеном другого проекта даёт 401. ACK через API меняет состояние на `acknowledged`. |
| MCP | `/mcp` требует отдельный bearer. Проверяется согласование всех четырёх поддерживаемых ревизий от `2024-11-05` до `2025-11-25`, включая 204 для `notifications/initialized`. Через HTTP и npm stdio проверяются схема `noticeplace`, запись отключения уведомлений и чтение общих настроек проекта. |
| SDK | Python wheel и npm tarball устанавливаются в отдельные каталоги. Python и Node SDK публикуют события и читают подтверждённые инциденты. Обе сборки SDK читают записи обеих ревизий через действующую версию сервиса, в том числе после отката. |
| Установка и откат | SHA Git-архива и SDK фиксируются в отчёте. Установленные файлы API и unit сверяются с исходным артефактом. Путь запуска, метаданные активного релиза и версия из `/health` проверяются на каждой стадии. Откат возвращает исходный каталог и читает через API все записи кандидата. |
| Токен проекта | При выпуске замены оба токена читают инцидент через API. После завершения замены новый токен читается на кандидате и после отката. Старый получает 401 в обоих случаях. |
| Архивы MCP | Сверяются контрольные суммы tar.gz и zip. После распаковки кандидат отвечает на `initialize` и `tools/list` из каждого архива. |
| Хранение | После каждой остановки отдельное SQLite-подключение только для чтения сверяет идентификаторы событий и инцидентов, текст, состояние, число вхождений и настройки отключения уведомлений. Проверяются `quick_check`, сохранение конфигурации и отсутствие отправок. После отката создаются новые записи. |

`receipt.json` содержит итог `pass` или `fail`, стадию проверки, SHA исходников, версии, SHA-256 артефактов и результаты чтения по стадиям. На ошибке процесс завершается с ненулевым кодом. Исходный артефакт каждой ревизии лежит в `previous/noticeplace-source.tar.gz` или `candidate/noticeplace-source.tar.gz`.

## Границы результата

- Фикстура охватывает одиночный SQLite и установку во временный каталог через `NOTICEPLACE_DESTDIR` с `--no-start`. Воркеры отключены. Активация systemd, автоматический откат после сбоя старта, Dqlite, внешние доставки и продуктивные потребители требуют собственных проверок.
- Старые архивы могли выпускаться без `notification_center`. При проверке прежней версии такие архивы отмечаются в отчёте. Новая сборка включает модуль, который нужен MCP для запуска.
- Проверяется завершённая ротация. Во время незавершённой ротации предыдущий сервер видит только действующий токен. Перед выкладкой старого релиза завершите или отмените замену.
- Проверка подтверждает перечисленные сценарии HTTP v1, MCP и SDK, включая чтение новой записи предыдущим сервером. Полные схемы методов, промышленный объём данных и обратимость произвольных миграций выходят за пределы фикстуры.
