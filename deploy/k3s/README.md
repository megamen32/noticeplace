# Необязательный пилот Kubernetes

NoticePlace API работает одним образом OCI в Docker Compose и K3s. Приложение
не обращается к Kubernetes API; база, Rust mesh core, доставка уведомлений и
телефон работают через существующие сервисы. Контейнер содержит только
приём событий и авторизованное чтение. Это позволяет менять способ запуска
API без переноса базы и без второго владельца внешних отправок.

На server44 проверен реальный K3s v1.37.1+k3s1: server и agent в отдельных
Docker-контейнерах, на одном физическом хосте. API принял новое событие,
штатный экземпляр прочитал его из общей базы, а уведомление было независимо
подтверждено в Telegram. Deployment пересоздал удалённый Pod за9.341с и
перенёс его на второй логический узел за9.543с после cordon и удаления Pod.
Весь сценарий занял19.690с при максимуме180с. Это проверка восстановления
приложения; физическая отказоустойчивость и HA управляющего контура не проверены.

API source: `01131783e483e429cd37569c1234c553cf53e0d3`.
Docker config identity:
`sha256:3a34b311b67c64f99de082cfdb0b064f1a93e044424681615c890b43bc3762a8`.
После реального Docker export/import containerd манифест получил digest
`sha256:410f797b088961b660bd4189f6c00b66e004733dbb4118354e8abb6d7d9c29b9`;
его config digest проверен и совпадает с Docker image identity. Образ импортирован
на оба узла и используется по digest с `imagePullPolicy: Never`.

`api.yaml` — шаблон этого пилота. Перед применением замените
`NOTICEPLACE_API_IMAGE` проверенным импортированным digest. Namespace
`noticeplace-pilot`, Secret `producer-api` и label `noticeplace-mesh-host=server44`
должны соответствовать подготовленным узлам. Secret получает тот же ограниченный
producer env, что описан в `../container/README.md`; provider, Telegram и
исполнительские ключи ему не нужны. ServiceAccount token в Pod отключён.
UID/GID996:995 соответствует реальным сокетам server44; другой физический
хост требует его собственных проверенных UID/GID и mesh identity.

Внешние K3s containers монтируют реальные каталоги
`/run/noticeplace-mesh` и `/run/noticeplace-mesh-core` read-only на оба узла;
Pod hostPath видит именно эти вложенные подключения. Используется каталог,
а не отдельный inode сокета. API получает RAM256MiB, CPU1, PID budget64,
rootfs read-only, tmpfs16MiB и никаких capabilities. Его реальный cgroup на
каждом из двух узлов проверен как потомок внешнего Docker budget.

Каждый K3s node ограничен RAM2GiB, CPU2, tasks1024 и нулевым swap:
Docker `--memory 2g --memory-swap 2g`, затем проверка `memory.swap.max=0`.
Restart policy `no`; журналы ограничены2×10MiB на узел. Данные и конфигурация
пилота доступны только root, kubeconfig0600. Внешние узлы используют privileged
режим штатного контейнерного примера K3s; они не получают host PID/network,
docker.sock, корневой каталог хоста или дополнительный writable host cgroup mount.
Ограничение ресурсов проверяется по родительскому Docker scope, включая Pods,
а не по неограниченному дочернему `init` cgroup. OOM/OOM-kill не наблюдался.

API Kubernetes опубликован только на127.0.0.1:16443; NodePort30095 — через
127.0.0.1:18096. Compose использует отдельный127.0.0.1:18095.
Отдельная bridge сеть172.31.240.0/24, Pod CIDR10.250.0.0/16 и Service
CIDR10.251.0.0/16 проверены на отсутствие пересечения с маршрутами хоста.
Traefik, ServiceLB, metrics-server, local storage, CoreDNS и Helm controller
для этого пилота отключены. Прямые applets `kubectl` и `ctr` работают внутри
контейнера; составной `k3s kubectl` в проверенном образе не работал.

На этом хосте VXLAN был недоступен во вложенной среде. Для двух узлов одной
L2 bridge выбран поддерживаемый `flannel-backend: host-gw`; недостающий,
уже установленный модуль ядра `xt_comment` загружен. Host-gw требует прямой
L2 связи между узлами и не подходит без повторной проверки для произвольных
узлов mesh через разные сети.

Измерение после переноса: Docker working set около554MiB на server и181MiB
на agent, против26MiB у отдельного API Compose. Родительские cgroup с file
cache показывали1171496960/476250112 bytes, пики1326174208/517881856 bytes.
Каталог данных и сохранённый архив пилота занимали967MiB. Это наблюдения
малого пилота, а не прогноз нагрузки всей системы.

После проверки оба принадлежащих пилоту K3s containers остановлены.
Compose действительно прочитал оба принятых события при полностью остановленном
Kubernetes. Оба контрольных уведомления закрыты через канонический
`POST /v1/events` с отдельными устойчивыми ключами; отправки и звонки не повторялись.
Приватные receipts и данные пилота сохранены на44 в
`/var/lib/noticeplace-mesh/k3s-pilot-20261013`. Основной mesh не перенесён в K3s.

Практический выбор: сохранять переносимый образ и Compose как самостоятельный
вариант. K3s полезен для автоматического размещения, обновления и восстановления
многих сервисов. Он добавляет собственный управляющий контур и не заменяет
кворум базы, fencing отправок или SIP failover. Постоянный кластер на нескольких
физических узлах — отдельное внедрение с собственными проверками и резервированием.
