# Повторные звонки и понятный итог инцидента

Статус: реализация и проверка.

Пользователь просит звонить об одной боли не чаще раза в час, дать видимый итог разбора/исправления и возможность проверить работу.

Причина: новые эпизоды одного source/host/signal обходят ограничения внутри инцидента. CPU и load одного сервера также создают отдельные эпизоды. Завершение диагностики/ошибка и восстановление producer не создавали доставляемого итогового сообщения; health.resolved очередь не допускала закрытые инциденты.

Решение: durable общий бюджет звонков project+recipient+host+семейство сигнала; CPU/load объединены, другие проблемы независимы. Default 3600 секунд, горячая настройка существующей операторской панели. Учитываются попытки, включая неясный результат; отмена в тихие часы не расходует бюджет. Повторы отменяются, не копятся для последующего массового обзвона. Никакого автоматического ослабления ограничения при emergency. Итоги информационные, без звонков и эскалаций, доставляются после ACK/resolve. Создание сессии не доказывает ремонт. Диагностика готовит планы с явным ожиданием выбора; успех ремонта требует прежней независимой verification/fingerprint gate. Самостоятельное исчезновение сигнала маркируется как восстановление мониторинга.

Бюджет проверки: один serial Python suite, timeout 180s; тестовые базы и артефакты под игнорируемой .tmp/, без браузерных пулов/GPU/native запусков. Сохраняем существующий host session guard, ≤2 CPU для тестового процесса через CPU affinity. Runtime live измерен: main ~34MiB, admin ~20MiB; установленные лимиты main 512MiB/1GiB RAM, 256MiB swap,2CPU/256tasks, admin256/512MiB,128MiB swap,1CPU/128tasks. Не меняем лимиты, пространство temp ≤100MiB, reduced IOWeight сохраняется.

Финальный canary: после review/tests/push/deploy один контрольный health notice + matching source recovery через настоящий HTTP/consumer; без звонка, без запуска агента. Проверить durable Telegram receipt + фактическое сообщение получателя. Herder/Codex/Mac не перезапускать. Старые неизвестные agent jobs не переигрывать.

Проверка/review: 14 новых queue/adapter регрессий покрывают CPU/load, новые correlation/incident IDs, cross-channel/cross-connection race, перезапуск и границу часа, bootstrap неизвестного прежнего звонка, другие host/signal/recipient, quiet/stale claim, hot setting, итог после ACK/resolve, отсутствие повторного/устаревшего итога, три подписанных плана, транспортный timeout. Red дополнительных связанных дефектов: отправленные карточки сессий мешали in-place публикации планов; корректный edit той же Telegram карточки ошибочно считался вторым физическим сообщением в health check. Исключены информационные карточки из plan reconciliation, подтверждённый in-place edit исходной отправленной карточки не считается новой карточкой. Разные исходные отправки по-прежнему требуют reconciliation. Не ослаблены gates проверки ремонта и неопределённых внешних доставок.

Операторская UI-проверка после deploy: одна собственная Chromium-сессия, два renderer, JS heap256MiB на renderer, общий outer session guard неизменен, CPU affinity2; dedicated profile/temp только .tmp/, без глобальных MCP и native harness запусков.
