# Notice Place: исследование и решение для полного цикла

Дата: 7 ноября 2026. Обязательное исследование: **17:25:05–17:45:05 UTC (20:25–20:45 МСК)**, далее оформление и проверка плана. Это результат исследования, а не отчёт об исправлении production. Код сервисов, правила, история и рабочие каналы в ходе исследования не менялись. Контролируемые запросы к Ollama выполняли только классификацию.

## Что должно работать

Человек отдыхает, пока система обнаруживает проблему, назначает ровно одного исполнителя с autopilot, получает свежую проверку источника и закрывает инцидент. В обычном случае сообщений человеку нет. Если исполнитель исчерпал разрешённые действия и нужен конкретный ответ — приходит один понятный вопрос; ответ возвращается в ту же сессию. Подтверждённая чрезвычайная ситуация уведомляет немедленно. Неисправность самого Notice Place имеет независимый аварийный маршрут.

Это меняет договор системы: доставка события и сообщения больше не считаются выполненной работой. Успешный запуск агента также не означает восстановления.

## Выбранная архитектура

### Сигнал, работа и обращение к человеку — разные сущности

Сигнал сохраняет наблюдение источника. Семейство проблемы имеет стабильные project/source/resource/rule идентификаторы. Эпизод хранит generation, повторяемость, owner session и текущее состояние. Доставка человеку разрешается только отдельным policy решением: emergency либо конкретный необходимый вопрос/действие после самостоятельной работы.

Повтор обновляет ту же проблему и текущую сессию. Изменение текста, IP или номера поста не должно автоматически создавать новую серию обращений. Но разные ресурсы и реальные независимые сбои нельзя бездумно склеивать. Identity берётся из явного source contract, не из разрезания строк по двоеточию.

Существующий Herder остаётся владельцем native sessions/autopilot. Runtime для incident repair — **OpenCode, minimax-coding-plan**, без скрытого fallback через OmniRoute. Gemma не получает инструменты, не исполняет ремонт и не закрывает инциденты. Сохранить human STOP, существующие receipt/outbox и запрет повторов UNKNOWN.

### SDK и независимая проверка

Не создавать второй orchestrator. В `notification_center/consumer_lifecycle.py` уже есть SourceVerifier: pull verification requests → свежая проверка → durable intent → POST check → reconciliation. `incident_lifecycle.py` уже различает work_finished и source-authoritative recovery. Публичный Python client пока этого полноценно не предоставляет.

SDK должен передавать версию схемы, source/host/resource/rule, observed_at/generation, симптомы, влияние, last-good, ограниченную диагностику, допустимые действия и ссылку на разрешённую проверку. Недостаточный контекст получает статус incomplete и запрос обогащения; это не основание игнорировать проблему.

Основной транспорт — **исходящий pull источника к существующему API**, с cursor, backoff/jitter, timeout и возобновлением. Существующие timers могут делать короткий опрос; optional long polling уменьшит пустые запросы. Webhook может быть подсказкой «есть работа», но потеря webhook не теряет проверку. GPTAdmin нужен там, где уже является разрешённым транспортом; не прокладывать через него обязательный дополнительный слой всем consumers.

Проверка относится к конкретной generation и имеет freshness/deadline. Старый healthy result, отчёт исполнителя и HTTP 200 от чужого сервиса не закрывают incident. Недоступный источник приводит к unknown и ограниченной работе в той же сессии, а не вечному молчанию или новому агенту каждую минуту.

### Классификация Gemma

На 44 уже работают Ollama и очередь; gemma4:latest реально отвечает. Digest `c6eb396dbd5992bbe3f5cdb947e8bbc0ee413d7c17e2beaae69f5d569cf982eb`; локальная модель сообщает architecture gemma4, 7 996 157 674 параметра, Q4_K_M. Не переносить на неё характеристики других одноимённых моделей.

На восьми заранее заданных синтетических примерах получено **6/8 правильных классов** и 8/8 совпадений needs_human. Два промаха: короткий сетевой сбой и недостаточный контекст модель назвала log вместо repair. Восемь запросов заняли 16–26 секунд каждый. Это проверка доступности и риска, не измерение production качества. Подробности сохранены в `research/gemma-synthetic-summary.json` как сводка tool outputs, а не оригинальные receipts.

Следовательно: сначала размеченный корпус и shadow, затем ограниченное включение. Emergency имеет детерминированный нижний порог; insufficient context → enrich/repair. Cache по значимому изменению, deadline, JSON schema, no tools, защищённые получатели и safe fallback. Отказ очереди не блокирует emergency. Сохранить существующий queue proxy и его управление ресурсами. Локальная Ollama не требует платного внешнего inference API, но вычисления и поддержка не равны нулевой стоимости.

Пользователь уточнил: **Kev Jared Palmer**. Официальные [README](https://github.com/jaredpalmer/kev) и [карта Kev-4B](https://huggingface.co/jaredpalmer/kev-4b/blob/main/README.md) прочитаны в этом исследовании. Kev — специализированный prefill-only classifier с LoRA и pointer head; официальный запуск — `python -m kev.serve`, API `/v1/systemone`, типы choice/noul/score. Документированного запуска через обычный Ollama API в изученных источниках нет: просто импорт базовых весов не доказывает сохранение head и calibration.

Начать сравнение можно с Kev-0.8B, затем проверить fit Kev-4B. Для 4B автор указывает около 16 ГБ свободной GPU памяти, а у 44 всего 12 ГБ; обещать fit совместно с Gemma нельзя. Карта заявляет English и относит другие языки к out-of-scope, поэтому русские инциденты и смешанные логи — обязательная часть отдельного теста. Результаты автора не заменяют наш корпус. K01 фиксирует runtime/resource feasibility, изолированное сравнение и выбранный маршрут; запуск production Kev пока не выполнен. Общий classifier interface допускает официальный Kev runtime, но существующую очередь Ollama не следует подменять ради названия модели. `pip install kev` устанавливает другой пакет: использовать только проверенный pinned официальный исходник.

### История 7 дней

Удалять подробные события, старые доставки, audit payload и закрытые/истёкшие эпизоды старше семи дней. Отдельно сохранить компактное текущее состояние живых проблем, rules/mutes, STOP и минимальные no-replay tombstones. Это не бесконечный архив логов: tombstone содержит только идентификатор/исход, необходимые для запрета повторного действия.

Старые open без свежего подтверждения — expire/archive, не recovered. Старые unanswered human requests истекают без фиктивного ответа и resume. Очистка bounded batches по preview, с измерением mesh latency и контролем ссылок/ключей. Первичный rollback snapshot имеет отдельный короткий срок; не создавать новый вечный backup-мусор. Бессрочный claim «всё удалено через 7 дней» не делать, пока явно сохраняются state и no-replay guards.

### Человек видит только необходимое

Пример важного сообщения:

> Smart Edge
>
> Внешний маршрут не восстановился после автоматического исправления. Сейчас часть сайтов недоступна.
>
> Нужен выбор: временно переключить маршрут или оставить текущий. Диагностику ведёт [подтверждённая сессия].

Это пример формата, не сообщение о текущем состоянии сети. Если действия человека не нужны, сообщение не отправляется. Успешное исправление хранится на доске; обязательных «принят/запускаю/готово» и ежедневных дайджестов по умолчанию нет. Уже показанная аварийная карточка может обновить состояние вместо нового сообщения.

Постоянное меню Telegram ведёт к настройкам; кнопки конкретной карточки открывают её правило. UI показывает scope, срок и фактический результат mute. Настройка должна работать для следующих эпизодов и после перезапуска, а не лишь менять текст кнопки.

## Поставка и приёмка

Приоритет первой волны: S01 тишина и агрегация отказов, S02 реальные mute/настройки, S04 Smart Edge; параллельно S13 Matrix и S15 независимый watchdog. Затем S03 быстрый UI, S05–S09 единая работа/SDK, S10–S12 classifier и retention, миграции всех источников. Источники, уже проверенные по новому контракту, поставляются по мере готовности, а не ждут последнего consumer.

Один Lead отвечает за интеграцию и итог. Названия owner в плане — роли будущих исполнителей, не утверждение, что агенты уже запущены. Сессии не создавались. Изменения в shared checkout — только собственные пути; main, без новых feature branches. У Notice Place чужой WIP в .gitignore/bin/notify-center и множество чужих untracked task files: они не входят в эту поставку.

Каждая поставка требует source SHA → artifact → installed hash → реальный consumer receipt. Unit tests и карточка plan PASS не заменяют runtime. Откат возвращает предыдущий известный artifact/config без удаления receipt/STOP/mute; обратно к спаму не откатывать молча — безопасная деградация сохраняет дедупликацию и emergency.

Финальные сценарии:

1. 1000 повторов и конкурентный приём одного дефекта → одна действующая repair session, ноль owner сообщений; разрыв/перезапуск worker не создаёт дублей.
2. Один настоящий блокер → одна тестовая карточка с подтверждённым исполнителем; ответ возвращается в тот же native session/turn. STOP и UNKNOWN соблюдены.
3. Emergency → одна доставка через разрешённый канал независимо от Gemma; повтор и recovery обновляют понятное состояние, не создают поток.
4. Только свежая source-owned healthy проверка нужной generation закрывает incident; stale/unknown/work_finished не закрывают.
5. Настройки открываются из карточки и постоянного меню; mute переживает новый IP, новый эпизод, reload и restart; scope не затрагивает чужой проект.
6. Dashboard: локальный API p95 <500 мс и полезный экран p95 <2 с на текущем объёме даже при недоступном Herder; цифры — целевые критерии, ещё не достигнуты.
7. TTL удаляет старую подробную историю; те же accepted action IDs после cleanup не исполняются вновь; активное состояние и настройки сохранены.
8. Matrix: изолированные bot accounts/room, соединение/звук/завершение и receipts. Тестовых звонков реальным людям, Android/PSTN fallback и тестовых owner уведомлений — ноль.
9. Telegram call: проверить фактический adapter и квитанции. Живой звонок нельзя считать проверенным по одной настройке. При отсутствии разрешённого bot-to-bot теста явно оставить доказательственный предел; не обходить запрет звонком владельцу.
10. Независимый vpn2 watchdog: реальный health auth исправен; изолированные outage/401/recovery доставляются тестовым адресатам, без основной системы.
11. После поставки — 24 часа автоматического наблюдения: повторы, unresolved without owner, verify age, queue latency, лишние обращения и новые source families. Это календарное ожидание; ручная QA владельца не нужна.

Полное покрытие доказывается сверкой registry с живыми enabled producers. Исторические 26 строк и 18 активных проектов — начальная карта, не доказательство полноты. QA/integration и retired consumers не включать в production ради галочки. Каждый новый найденный producer получает собственную задачу до заявления complete.

## Открытые вопросы, которые нельзя скрыть оценкой

- Точная первопричина shell exit 1 ATV пока не установлена; S05 начинает с исследования без replay старого job.
- Живой Telegram voice capability и допустимая автоматическая проверка пока не подтверждены; S14 отдельно фиксирует границу.
- Полный runtime inventory всех источников не завершён; S16 сопоставляет IDs, hosts и owners перед миграцией.
- Kev идентифицирован, но его runtime на 44, размещение в памяти и качество русского языка ещё не проверены. Это ограниченное исследование K01, не причина откладывать исправление уведомлений.

Плановые 15-минутные листья — ограниченные единицы работы на существующих реализациях. Если проверка обнаруживает более глубокий дефект, он раскладывается в дополнительные листья и прогноз пересматривается. Нельзя выдавать сумму первоначальных оценок за гарантированный срок при этих неизвестных.
