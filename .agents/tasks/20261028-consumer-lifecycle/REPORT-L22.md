# L22 — ограниченная миграция истории lifecycle

Исправлена причина падения установленного API: старый `initialize()` возвращал всю историю `health.degraded` одним SQL-ответом, превышавшим защитный лимит mesh 16 MiB. Рабочая версия API восстановлена release_core до этой работы; этот лист не выполнял установку, миграцию или запись в production.

Изменение ограничено `notification_center/incident_lifecycle.py` и `tests/test_incident_lifecycle.py`. Все три исторические выборки — события, принятые квитанции и старые профили — используют общий PK-keyset reader без OFFSET. Сначала возвращаются максимум 128 числовых ключей и размеров, затем читается только префикс с суммарным сырым размером не более 1 MiB, включая запас на строки. При максимальном шестикратном JSON-экранировании это менее 6 MiB плюс небольшой заголовок, существенно ниже рамки mesh 16 MiB. Одна строка, превышающая бюджет, явно отклоняется, а не пропускается. Производственный максимум payload ниже бюджета на два порядка.

События обходятся по монотонному `e.rowid`, с `events NOT INDEXED`, без повторной полной сортировки истории по времени. Последнее значение группы выбирается отдельным сравнением `(created_at,rowid)`, поэтому исходная семантика сохранена даже при несовпадении времени и порядка вставки. Число поколений и максимальный `observed_at` сохраняются. Создаётся одна проекция на инцидент; синтетическое восстановление, попытка агента или отправка не создаются. Уже существующие проекции исключаются следующим запуском через NOT EXISTS.

## Доказательство

- RED: `python3 -m pytest tests/test_incident_lifecycle.py -q -k historical_initialization_respects` упал с `sqlite3.OperationalError: bounded SQL result exceeded` ровно на старой строке 79. Адаптер ограничивает фактический сериализованный SQL-ответ, а не просто проверяет наличие LIMIT.
- GREEN: полный `python3 -m pytest tests/test_incident_lifecycle.py -q` — **40 passed in 47.30s**. Регрессия покрывает несколько страниц всех трёх выборок, последнюю неполную страницу, повторную инициализацию, переставленные timestamps и точное сохранение принятых квитанций/continuation без новой доставки.
- Read-only metadata производственного mesh на server-100: **188598** событий, **2100** различных инцидентов; агрегат выполнился за **0.130 s**. Максимальный payload — **5579 bytes**. Первая PK-страница из 128 строк: **123405 raw bytes**, **0.002 s**.
- Затем тот же новый `_migration_rows` прочитал всю живую историю через `Connection(..., readonly=True)`: **188599 events**, **2949 SQL calls**, **29.645 s**, максимум payload **5579 bytes**. Дополнительное событие появилось от существующего фонового источника между чтениями; этот лист событий не отправлял. Вывод содержал только счётчики и время, без payload или секретов.
- Полный read-only проход не запускал `initialize()`, DDL, INSERT/UPDATE, миграцию либо HTTP-события. Старый runtime после rollback не содержит таблицы `incident_lifecycle`; поэтому этот проход использовал эквивалент полного первого чтения событий без фильтра уже созданных проекций.

Первый запуск после установки требует полного чтения и около 2100 вставок проекций, а не 188599 записей. Release_core уведомлён: сначала один API на server-100 с ограниченным окном готовности около 90 секунд, затем server-44 и server-88. Установка, готовность авторизации и один безопасный сквозной тест остаются отдельной обязательной приёмкой; этот отчёт подтверждает исходники и read-only совместимость SQL.

## Адресная поправка после ревью

Ревью воспроизвело ещё один RED: три старые принятые квитанции одного request_id с evidence по 1600 символов и бюджетом страницы 4096 байт переносили `legacy:unknown:0` вместо последней `legacy:unknown:2`. Обновление nonce после первой страницы исключало остальные квитанции из JOIN. Узкая поправка выбирает `MAX(rowid)` для каждого request_id через существующий индекс до постраничного обхода. Проверка `python3 -m pytest tests/test_incident_lifecycle.py -q -k 'legacy_receipt_pages_keep_latest or historical_initialization_respects or additive_upgrade'` дала **3 passed in 3.60s**. Новая регрессия проверяет точную последнюю квитанцию, evidence и continuation для unknown и degraded. Историческая и профильная выборки не менялись; повторный полный production read-only проход и runtime-операции не выполнялись.
