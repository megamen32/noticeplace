# Восстановление ролей consumer-lifecycle в карте токенов NoticePlace

## Цель

Вернуть в `/etc/notification-center.env` (100/44/88) поля `incident_role`,
`principal_id`, `verification_sources`, `verification_owned_sources` для 53
токенов, которые 30 октября потеряли их при записи через admin-консоль, и
восстановить рабочий переход «исполнитель отчитался → источник проверил →
инцидент закрыт» (`work-finished` → `check-result`), который сейчас даёт 401.

## Бизнес-результат

fleet-health (и остальные health-потребители) снова могут закрывать свои
инциденты: исполнитель отмечает работу через `work-finished` токеном
исполнителя, источник подтверждает восстановление независимым `check-result`.
Сегодня переход невозможен — 401 «source verification credentials cannot
finish executor attempts», и инциденты накапливаются открытыми.

## Установленная причина (проверена на живых данных)

1. 26.10 — в карте было 26 проектов, по одному токену на проект.
2. 28.10 19:28 — применён reviewed-план consumer-lifecycle: карта выросла до
   53 токенов (по два на проект: `verifier`=источник и `executor`=исполнитель),
   у всех появились `incident_role`, `principal_id`; у 11 из них —
   `verification_sources`.
   Артефакт этого состояния сохранён:
   `/var/lib/notification-center-admin/rollbacks/1793319447-32213782/notification-center.env`
   (`base_scope_hash`=`94c2d6d7…`, `candidate_scope_hash`=`8914b2fd…`).
3. 30.10 03:17 — admin-консоль выполнила `project_created` для проекта
   «Олег и Никита». Её `_scopes()` нормализует карту, оставляя только
   `project`, `max_severity`, `agent_jobs`, `automatic_health_diagnosis`, и
   **теряет все v2-поля**. После этого все 53 токена стали обычными.
   Доказано на живом коде: 53 v2-токена → 53 plain, `incident_role` сохранён у 0.
   Потеря видна и по времени: 30.10 04:02 env переписан в Unicode-версии уже
   без v2-полей.
4. 30.10 15:44 — admin-консоль создала ещё один токен («Олег и Никита»),
   карта стала 54 токена. Дубли «источник + исполнитель» — **не мусор**:
   это штатная пара, предусмотренная reviewed-планом.

Итог: дефект — не в плане и не в дубликатах, а в потере v2-полей при записи
через консоль. Скрипт `scripts/sync-health-callback-tokens.py` при этом
работает корректно: он сам проверяет `lifecycle_v2` и отказывается молча
переписать callback-карту, если роли потеряны.

## Что подтверждено как безопасное

- Значения токенов не меняются: v2-карта ⊂ живой карты по значениям.
- Политические поля не меняются: 0 расхождений по `max_severity`,
  `agent_jobs`, `automatic_health_diagnosis` между v2-артефактом и живой картой.
- Callback-карта `/home/roomhacker/.config/gptadmin/health-callback.json`
  уже содержит правильные executor-токены (27 проектов, совпадают с
  candidate-артефактом) — менять её не нужно.
- Поля `verification_sources` покрывают живые source_id; исторические
  (`historical-unbound`) закрываются через `exact`-правило.

## Известный побочный эффект, требующий миграции

36 эпизодов в БД привязаны к `credential:<sha256(токен)>` — это старый
principal, вычисляемый из значения токена. После восстановления ролей
principal станет именованным (`source:fleet-health` и т.д.), и `bind_source`
перестанет совпадать: эпизод перестанет принимать повторные события от
источника и проверку. Нужна однократная миграция `source_principal`:
`credential:<sha256(токен)>` → `<principal_id>` по таблице соответствия
(36 строк, вычисляется из v2-карты). Миграция локальна, аддитивна и проверяема
пошагово: после неё эпизод остаётся тем же самым (`incident_id` не меняется),
меняется только имя владельца-источника.

## Как проверим

1. `work-finished` executor-токеном fleet-health на реальном открытом эпизоде
   `inc_50a3d5274cbe4b9388ec9f9973787df6` возвращает 200 и оставляет инцидент
   открытым (ожидается: verification_state='due', попытка исполнения записана).
2. Независимый `check-result` источником fleet-health на том же эпизоде
   возвращает 200 и закрывает инцидент.
3. Доставка живого health-сигнала fleet-health (server-44) создаёт эпизод,
   привязанный к `source:fleet-health`, и он принимает повторные события.
4. Карта на 100/44/88 идентична по scope-хешу; `incident_role` присутствует у
   всех v2-токенов; callback-карта содержит executor-токен для каждого
   проекта.
5. Регрессия: консоль больше не теряет v2-поля при любом действии (тест на
   живой карте: нормализация сохраняет роли).

## Ограничения

- Не трогать продюсерские токены (`NOTIFY_CENTER_TOKEN` в `/etc/fleet-health.env`,
  `/etc/fail2ban/notify-center.env`, `/etc/gptadmin/notify.env`,
  `/etc/telegramauto-ha/tgc/runtime*.env`, `/etc/noticeplace-voice-mcp.env`,
  `/etc/fail2ban/notify-center.env` на 44/88) — их значения не меняются,
  они уже совпадают с восстанавливаемыми токенами.
- Не создавать новых токенов и проектов; «Олег и Никита» остаётся единственным
  проектом без reviewed-роли (обычный plain-токен, как сейчас).
- Не публиковать значения токенов в отчётах, логах и чатах.
- Не трогать чужие worktree/ветки; коммит — только в основной checkout
  `megamen32/noticeplace` по путям этой задачи.
- Только server-100/44/88, порты и БД каждого узла сохраняются.
